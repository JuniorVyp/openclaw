# OpenClaw — Task List E2E 360°

## 1. Objetivo e escopo

Esta lista consolida o histórico da conversa, a checklist de aprovação **PRD + Blueprint**, a backlog de issues de cobertura 360° e o primeiro incremento já incorporado à codebase. O objetivo é transformar os 28 blocos de aprovação em uma sequência executável de tasks que atravesse o fluxo completo: **entrada, validação, processamento, decisão, saída, recuperação e monitoramento**.

A priorização usa quatro níveis. **P0** representa risco crítico para o caminho principal, segurança, integridade de dados ou capacidade de liberar o produto. **P1** representa cobertura funcional e técnica essencial para uma release confiável. **P2** representa endurecimento operacional, escala, governança e superfícies secundárias. **P3** representa fechamento documental, otimização e readiness final.

> **Definition of Done global:** cada task precisa ter owner, evidência reproduzível, cenário ou teste identificável, critério de aceite mensurável, registro de falhas e integração ao gate apropriado. Nenhuma task pode ser considerada concluída apenas por documentação narrativa.

## 2. Baseline já implementado

O primeiro incremento foi consolidado no commit `2d973fbdae3` (`feat(qa): add 360-degree E2E coverage gates`). O baseline atual possui um contrato declarativo em `qa/e2e-360-coverage.yaml`, um gate de rastreabilidade em `scripts/check-e2e-360-coverage.mts`, um gate de performance em `scripts/check-e2e-360-performance.mts` e uma lane `checks-fast-e2e-360-coverage` no CI.

O contrato inicial evoluiu para **7 stages**, **4 proof kinds**, **23 requisitos**, **26 provas**, **7 fault injections** e **44 coverage IDs**. A validação realizada contra o catálogo QA retornou **529 cenários**, todos os stages cobertos e **zero issues de validação**. A nova evidência real valida **24 cenários**, timing positivo em **100%** das entradas e primary coverage por cenário. O gate de performance continua protegido por budgets de p50/p95/p99 e a bateria crítica anterior passou com **145 testes aprovados**, além de lint e formatação sem erros.

## 3. Ordem de execução recomendada

A execução deve seguir as ondas abaixo. A **Onda 0** fecha o contrato de produto, arquitetura e evidência. A **Onda 1** valida o caminho crítico de runtime. A **Onda 2** amplia a cobertura para segurança, dados, escala e superfícies secundárias. A **Onda 3** fecha governança, documentação, operação e aprovação final.

| Onda   | Prioridades   | Resultado esperado                                                           |
| ------ | ------------- | ---------------------------------------------------------------------------- |
| Onda 0 | P0-01 a P0-13 | Caminho crítico rastreável, seguro, observável e protegido por CI            |
| Onda 1 | P1-01 a P1-18 | Cobertura funcional dos canais, agentes, providers, ferramentas e interfaces |
| Onda 2 | P2-01 a P2-13 | Endurecimento de segurança, dados, escala, deployment e governança           |
| Onda 3 | P3-01 a P3-04 | Checklist PRD + Blueprint aprovado e release pronta para decisão             |

## 5. Gates transversais

As tasks devem convergir para os seguintes gates. O gate de rastreabilidade deve impedir cenários sem primary ownership, coverage IDs desconhecidos, stages ausentes ou proof kinds não exercitados. O gate de performance deve bloquear regressões de P95/P99 e qualquer duplicate side effect. O gate de segurança deve falhar diante de secret leakage, autorização ausente, ferramenta executada antes da aprovação ou artefato de suporte com payload sensível. O gate de resiliência deve provar restart, retry, reconnect e fault injection com recuperação observável. O gate de release deve exigir DoR/DoD preenchido, mapa dos 28 blocos, evidências, owners e aprovação registrada.

| Gate           | Entrada                                                    | Bloqueia quando                                                                           |
| -------------- | ---------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Traceability   | PRD, Blueprint, contract YAML, scenario catalog            | Requisito sem cenário, cenário sem primary coverage, stage/proof/fault ausente            |
| Functional E2E | Golden paths, channel/provider/UI/CLI scenarios            | Output incorreto, estado perdido, rota cruzada, erro silencioso ou side effect indevido   |
| Performance    | Samples reais, load/soak reports, budgets                  | P95/P99 acima do limite, throughput insuficiente, memory leak ou duplicate side effect    |
| Security       | RBAC matrix, approval tests, secret scans, redaction tests | Acesso indevido, secret em artefato, tool pré-aprovada ou auditoria incompleta            |
| Resilience     | Fault injection, restart/reconnect/retry scenarios         | Crash não recuperado, retry infinito, duplicidade, perda de evento ou trace inconsistente |
| Governance     | PRD + Blueprint checklist, risk register, approvals        | Lacuna sem owner, risco sem mitigação, documentação incompleta ou aprovação ausente       |
| Release        | Todos os gates anteriores                                  | Qualquer gate vermelho ou ressalva crítica sem aceitação formal                           |
